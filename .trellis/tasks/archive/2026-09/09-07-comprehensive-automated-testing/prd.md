# 全面自动化测试与缺陷发现

## 目标与价值

针对当前工作区的后端领域重构、前端 API repository 切换和相关未提交改动，建立一套可重复、快速反馈的高风险优先自动化回归验证。测试要覆盖用户可观察的管理与 LLM 请求行为；每个确认的缺陷都留下可复现的证据，便于后续单独修复。除非用户另行授权，本任务不修改产品实现、不自动提交。

## 追加授权（2026-09-07）

用户明确要求修复本任务发现的 BUG-001 和 BUG-002。本任务允许在前端 `apiUsers`、`apiVendors` repository 及其直接回归测试中做最小产品修复；页面级按钮由独立的 `09-07-frontend-user-interaction-testing` 子任务负责，该子任务可修复其范围内稳定复现的前端交互缺陷（本轮 BUG-003）。后端和无关工作区改动仍不在范围内。

## 已确认事实

- 根目录使用 Vitest Node 模式，测试服务器、SQLite 数据库和 mock 上游由 `tests/globalSetup.ts` 统一管理，测试文件串行执行以避免端口和数据库冲突。
- 任务开始时仓库已有 93 个后端测试文件/981 个 `it` 用例，以及 7 个前端测试文件/32 个 `it` 用例；现有测试已经覆盖协议转换、基础 CRUD、部分路由和计费场景。
- 本次工作区改动集中在 `user_key`/分组鉴权、模型上游路由、并发租约、计费结算、迁移、记录，以及前端 `repositories/`、stores 和管理页面。
- 任务开始时新增或重写的 `accessPolicyService`、`authContextService`、`concurrencyService`、`billingService` 和 `api*` repository 没有与其风险相称的直接测试；现有 API 测试不能替代所有纯规则和错误分支测试。
- 项目测试手册要求优先聚焦测试；本任务门禁包括 Node/SQLite 后端套件、后端类型检查和一次前端构建，不启动 D1 或 Worker。
- 工作区在任务开始时已有大量用户未提交改动；本任务必须保留这些改动，并隔离新增测试、任务文档和缺陷记录。

## 需求

### R1. 建立可追踪的测试矩阵

将用户/Key/分组、管理 CRUD、LLM 三协议、模型可见策略、上游筛选与调度、并发租约、流式/非流式收尾、计费和迁移等关键契约映射到具体测试文件、命令和结果。矩阵必须标出正向、负向、边界和异常退出路径，不能只统计用例数量。

### R2. 补齐后端高风险覆盖

- 纯规则：Key 摘要认证、root/admin 角色、状态/过期、IPv4/CIDR 和黑白名单、协议/模型白名单、额度/余额门禁。
- 数据与 API：多 Key 原子替换、重复摘要、分组 CRUD/引用清理、规范 DTO、鉴权错误 JSON、敏感字段脱敏和不存在资源。
- 路由与资源：分组/协议/健康/容量过滤，优先级层级、负载因子权重、失败排除和所有退出路径的租约释放。
- 计费与记录：token/per-request/image、缓存 token、倍率和整数微元、Key 与用户余额临界值、失败/取消不扣费、重复 finalize 幂等及记录快照。
- 迁移与兼容：仅验证 Node/SQLite schema/约束、迁移可重复性和孤儿引用；不触碰 D1、Worker 或未知 MySQL 实例。

### R3. 补齐前端 API 边界覆盖

验证 API repository 的序列化、字段归一化、列表 `{ list, total }`、404 转换、错误传播和批量空输入；验证 stores 的加载去重、分页合并、刷新、CRUD 缓存同步、失败后的状态恢复，以及用户/分组/供应商/模型引用变更不丢字段。关键页面行为沿用现有无障碍和反馈边界，不依赖真实后端。

### R4. 覆盖关键前端按键与交互

对所有会改变数据、权限、路由或后台请求状态的可点击控件做组件级自动化验证：登录提交、退出登录、列表搜索/重置/刷新、用户/Key 新建编辑保存、Key 添加/删除/重新生成、分组/供应商/模型新建编辑删除与测试、供应商模型获取、模型上游添加/删除/测试、余额调整、记录详情删除/前后切换/复制/下载、设置保存/取消/检查更新/清理记录、仪表盘自动刷新。断言点击后的调用参数、确认弹窗、事件/路由、loading/disabled、成功反馈和失败恢复；纯装饰性图标只做可访问名称检查。

### R5. 快速、分层地执行并记录

先执行受影响的最小集合并并行运行与后端隔离的前端检查；确认环境稳定后执行 Node 后端全量和前端构建/类型/lint。禁止访问真实供应商 API。每个失败先区分测试缺陷、环境故障、预期变更和产品缺陷，再将确认的产品缺陷写入任务内结构化记录。

### R6. 缺陷记录可复现

在 `findings.md` 中为每个确认问题记录唯一 ID、严重度、组件、前置数据、精确命令/用例、复现步骤、期望与实际、证据路径/行号、影响、临时规避（如有）和状态。无法稳定复现的问题标记为 `unconfirmed`，不能当作已确认缺陷结案。

## 范围外

- 除“追加授权”明确列出的 BUG-001/BUG-002 外，本任务不修复后端或前端产品代码；页面交互问题由独立子任务按其授权处理，其他问题只记录并可另开任务。
- 不调用真实 OpenAI/Anthropic 或其他供应商，不做压力/长时间稳定性基准，不引入浏览器 E2E 框架。
- 不启动 D1/Worker，不要求 MySQL 全量测试，也不触碰未明确授权的数据库实例。
- 不重写现有测试体系、不删除与本任务无关的测试，不提交 `test.db`、日志、构建产物、env 或 IDE 文件。

- D1/Worker 明确排除，不对其跨 isolate 并发或 binding 行为做结论。
- MySQL 端口可能存在但未必有凭据；本任务不连接该实例，只运行 Node/SQLite 验证。
- 现有大套件串行且会启动测试服务器，首轮按风险分层以控制反馈时间；全量结果仍作为最终质量信号。
