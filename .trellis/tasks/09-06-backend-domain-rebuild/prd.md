# 后端领域模型与运行链路重构

## 目标

以当前前端已经确定的用户、Key、分组、供应商和模型语义为后端唯一产品契约，完成一次性领域重构。运行时不再读取旧的 `user.token`、`model.routing_mode` 或 `model.routing_config` 语义，也不保留旧字段别名、双写或按旧格式回退。

## 已确认边界

- 默认保留当前 Hono + TypeScript、Node/SQLite（以及现有 Worker/D1 构建能力）作为本任务的代码基线；不在本任务中改成 Go 服务。
- `sub2api` 只作为设计参考：借鉴 API Key 鉴权阶段划分、IP 规则、并发租约、优先级/权重调度、预扣/结算/幂等等模式，不直接复制其领域模型或代码。
- 保留本项目已有的 OpenAI Chat、OpenAI Responses、Anthropic Messages 协议入口、协议转换、插件、请求记录和对象存储能力。
- 允许一次性数据库迁移和数据导入；这是升级工具，不是线上兼容层。默认迁移已有数据，迁移完成后旧列和旧运行逻辑删除。
- 管理 API 的响应以当前前端类型为准：用户/Key 与分组使用当前 camelCase 领域字段，供应商/模型保留当前页面使用的字段名；不增加旧 DTO 兼容别名。

## 需求

### R1. 用户 Key 与分组

- 用户可以拥有多个全局唯一 Key；Key 必须单独持久化并关联一个可空分组。
- Key 支持启停、名称、模型白名单、IP 白/黑名单、额度（人民币）、最大并发和过期时间。
- LLM 请求必须先解析 Key，再加载用户和分组；用户、Key、分组任一停用或 Key 过期时拒绝请求。
- IP 限制、Key 模型白名单、分组协议白名单和分组模型白名单在请求进入路由前完成校验，拒绝时返回协议一致的 JSON 错误。
- 管理端保存用户基本信息和全部 Key 时必须原子替换，不能留下半更新状态。

### R2. 供应商与模型路由

- 供应商的 `concurrency`、`load_factor`、`priority`、`group_id`、状态和协议能力成为可查询、可校验的正式字段，不再只存在于未序列化的临时对象中。
- 模型以 `mapping.upstreams[]` 为唯一配置入口；每个上游包含供应商、可选供应商模型和启用状态。旧 `routing_mode/routing_config` 不再作为 API 或运行时输入。
- 路由候选必须同时满足模型映射、供应商状态、Key 分组、入站协议、供应商协议能力、健康冷却和并发容量。
- 调度先按优先级选择可用层，再按负载因子进行加权；失败切换不能重复选择同一上游，所有租约必须在成功、失败、异常和客户端断开时释放。

### R3. 计费与记录

- 统一使用整数微元保存人民币金额；API 的价格/额度仍按前端约定的元展示。
- 支持 `token`、`per_request`、`image` 三种计费模式，缓存读写价格不能丢失；分组倍率作用于最终用户费用。
- 请求开始时执行可配置的预留/资格检查，结束时按实际 usage 结算；失败、取消和重复回调必须幂等，不得重复扣费或泄漏并发租约。
- Key 额度与用户余额都要参与扣费判断；记录至少保存 `user_id`、`key_id`、`group_id`、请求模型、命中供应商/上游模型、协议、usage、原始费用、倍率和最终费用。

### R4. 管理 API 与前端接入

- 新增分组 CRUD；用户 CRUD 和 Key 批量保存使用当前前端契约；供应商和模型 CRUD 接受当前页面提交的字段。
- 管理接口统一列表返回 `{ list, total }`，不存在资源显式返回 JSON 404/业务错误。
- 前端管理 repository 后续可以直接替换为 API repository，不需要在后端或组件中保留旧字段适配器。

### R5. 数据、安全与质量

- 迁移前提供可恢复的数据库备份/导入步骤；迁移脚本可重复检测并拒绝半迁移状态。
- Key 不写入普通日志；认证查询使用不可逆摘要/前缀索引或等效安全方案，管理端仅在明确授权的响应中返回必要的值。
- SQLite/D1 与 MySQL 的迁移和查询保持可验证；不能引入只在单一方言工作的 JSON 查询。
- 为鉴权、策略拒绝、调度权重/优先级、租约释放、计费幂等和新 DTO 增加单元/API/集成测试。

## 不做

- 不恢复 `keyGroups`、旧 `user.token`、旧 `routing_mode/routing_config` 的运行时兼容。
- 不把 sub2api 的订阅、账号多对多、美元计费、支付和大量平台专属字段搬进本项目。
- 不在本任务中重写前端视觉，也不在没有明确决定前提下切换 Go/PostgreSQL/Redis 作为唯一部署基线。

## 验收标准

- [ ] 新数据库模型和管理 API 能完整承载当前前端用户/Key、分组、供应商、模型字段。
- [ ] LLM 请求按 Key → 用户/分组策略 → 模型上游 → 并发租约 → 协议转换 → 结算的顺序执行，并在所有退出路径释放资源。
- [ ] 旧字段不再出现在新运行链路和新 API DTO 中；一次性迁移后旧列可安全删除。
- [ ] 关键拒绝/路由/计费场景有自动化测试，Node 类型检查和前端构建通过。
- [ ] 文档说明迁移、回滚、运行参数和当前已知的 Worker/D1 并发边界。
